(These notes are written for version 1.0)  

The final executable sits at roughly 750 KB raw and compresses down to ~300 KB
via UPX. The small footprint comes down to a few specific architectural choices:

1. Runtime and dependency minimization

  - Pure C99 over C++:
    Choosing C99 over C++ eliminates compiler-generated runtime overhead.
    There is no runtime type information (RTTI), no exception handling tables
    or stack-unwinding code, and no standard template library (STL) code bloat.

  - Direct Win32 and GDI instead of GUI frameworks:
    Frameworks like JUCE, Qt, or wxWidgets typically add 15 to 50 MB of binary
    overhead just to bootstrap an event loop and basic widgets. Instead, the UI
    is built directly against the native Win32 API (CreateWindowEx, custom
    WndProc loops, and WM_PAINT handlers). Rendering relies on raw GDI
    primitives (MoveToEx/LineTo) and direct pixel buffers (CreateDIBSection)
    rather than COM-heavy subsystems like Direct2D or GDI+.

  - Minimal system imports:
    The binary only imports from core Windows system DLLs that are already
    resident in memory: kernel32.dll, user32.dll, gdi32.dll, and msimg32.dll
    (for AlphaBlend). It does not depend on external runtimes.

2. Compilation model and dead-code stripping

  - Single-translation-unit (unity build) architecture:
    The project is structured with functions declared static inline across
    headers and compiled in a single pass. Because the compiler sees the entire
    codebase at once, it can:

      - Inline small, hot routines across subsystems without function call
        overhead.
      - Perform global constant propagation.
      - Identify and completely discard any static function that is never
        called (dead-code elimination).

  - Procedural UI over Win32 resource scripts:
    Utility windows (EQ panel, keybind list, tempo settings) are created
    dynamically at runtime rather than loaded from compiled resource (.rc)
    files. This avoids bloating the PE resource section.

3. Purpose-built tools vs. generic libraries

  - Targeted LZ compression (replacing zlib):
    Linking zlib or libdeflate adds a few hundred kilobytes of generic
    decompression logic. Since the project only needs to compress audio float
    data, it uses a small, hand-rolled LZ compressor (csq_compress_lz) with a
    fixed 8,192-entry hash table. It provides sufficient compression for project
    files while adding almost nothing to the binary size.

  - Direct struct serialization (replacing JSON/XML):
    Project saving and loading is handled by directly reading and writing flat
    C structs to disk (fwrite and fread). This eliminates the need for
    tokenizers, schema validators, or DOM tree allocators.

  - Minimal audio layer (miniaudio.h):
    Audio backend communication is handled via miniaudio as a single-header
    implementation, compiled so that only the necessary playback paths are
    built into the binary.

  - Scalar DSP routines:
    Biquad filter calculations, rate conversions, and timeline math are
    implemented in plain scalar C. This avoids linking heavy external signal
    processing or math runtimes.

4. Memory model and packaging

  - Static allocation over dynamic heap containers:
    Data structures (such as track clips and sample pools) use fixed-size global
    and stack buffers rather than dynamic resizing containers. This keeps the
    memory layout deterministic, avoids fragmentation, and eliminates reliance
    on complex heap allocation code.

  - UPX packing:
    The initialized code and data sections of the 750 KB PE binary are
    compressed using UPX. At startup, the stub unpacks the program into memory
    with negligible launch latency, bringing the final distribution size down
    to ~300 KB.
